# GitHub: восстановление проверок и управляемой автоматизации

Рабочий документ для текущего репозитория сайта. Это не подтверждение настроенной автоматической публикации или автоматического слияния. Не добавлять сюда секреты, токены и ключи.

## Подтверждено проверкой GitHub

- Пользователь включил разрешение auto-merge в настройках репозитория. Само разрешение **не включает** автослияние всех запросов.
- Пользователь создал набор правил «Проверка основной ветки»: цель — ветка по умолчанию, статус **disabled**, обязательный `validate` от GitHub Actions, запрет удаления и force push, без обходящих акторов. При выключенном статусе эти требования не действуют.
- Ранее `main` не имела активной защиты обязательной проверкой. Изменять правило и проверять настройки Actions через текущую интеграцию невозможно: API возвращал 403. Нельзя делать вывод, что у владельца аккаунта нет административных прав: права интеграции и права владельца — разные вещи.
- `Site checks` содержит задание `validate`; в соответствующих запусках PR выполняются браузерные и другие проверки. PR #139 обновлён Dependabot и прошёл проверки; PR #144 подготовлен в текущей ветке. Повторно проверять состояние перед решениями.
- В PR #144 добавлено ограничение: ручной запуск новостного workflow на ветке, отличной от `main`, пропускает всё задание и использует отдельную группу конкуренции. Это не тестирование самой публикации.
- `Update News` и `Update open logistics indicators` при изменениях делают прямой push в `main`. Наличие локальных тестов **перед** push не создаёт на GitHub обязательный статус `validate` для нового коммита. Доступ к данным или их публикация не гарантируются результатом теста.
- В PR #144 подготовлено сохранение публичных выходных файлов как артефактов на 7 дней, если этап push не прошёл. Это только аварийная копия; сайт сам по ней не обновится, доступность артефактов и их восстановление на практике не проверены.

## Инструкции GitHub и последствия для проекта

1. [Правила защиты и обязательные статусы](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets): статус относится к конкретному коммиту. Правило может запретить обновление ветки, пока проверка не завершена. Список исключений позволяет обходить правило — такой обход не означает проверку. Выбор `validate` от GitHub Actions ограничивает источник результата.
2. [Запуск workflow из другого workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow): обычный push, сделанный встроенным `GITHUB_TOKEN`, не запускает новый `push` workflow; существуют документированные исключения для ручных событий и событий создания/обновления PR, причём PR от встроенного токена может требовать разрешения владельца на запуск. GitHub отдельно указывает, что коммиты, отправленные с `GITHUB_TOKEN`, не запускают сборку GitHub Pages. Поэтому прямой push может обновить репозиторий, не обновив сайт; зелёный запуск сборщика сам по себе не подтверждает публикацию. Доступ внешних токенов, правила и способ подтверждения надо проверять отдельно.
3. [Автослияние PR](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request): функция доступна при включении в репозитории и включается для конкретного запроса, затем ждёт обязательных условий. Разрешение функции не является политикой «сливать всё».
4. [Автоматизация Dependabot](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/automate-dependabot-with-actions): возможна отборная автоматизация с учётом типа обновления и зависимости. Обновления не равнозначны: для локально включённых Chart.js, Leaflet и Font Awesome обновление пакета требует согласованного изменения файлов и лицензий. Сценарий не включён и не проверен.
5. [Разрешения GitHub Actions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository): право workflows создавать или одобрять PR настраивается отдельно от разрешения автослияния. Текущее значение через интеграцию не удалось проверить; не включать глобально без оценки рисков.
6. [Безопасность Actions](https://docs.github.com/en/actions/reference/security/secure-use): минимальные разрешения для каждой задачи; не запускать непроверенный код или артефакты чужого PR в привилегированном `workflow_run`/`pull_request_target`. Секреты не помещать в рабочие данные, файлы или журнал.

## Безопасная последовательность внедрения

1. Не включать подготовленное правило до испытания пути обновлений. Не добавлять общий обход для всех Actions: он позволил бы пропускать обязательный статус.
2. Проверить публикацию новостей и открытых данных на изолированных тестовых изменениях без production-пуша и без персональных данных; определить, какие файлы, включая архивы, должны попадать в результат. Сохранение в артефакт протестировать фактическим запуском и скачиванием, а не только чтением YAML. Ограниченный срок хранения не равен резервному копированию.
3. Разработать путь, при котором GitHub проверит **тот же коммит**, который предлагается к публикации, и результаты не потеряются при параллельных обновлениях; сохранить явный сигнал об ошибке и не отключать проверки. Новые полномочия и автоматические операции сначала испытать в безопасной среде. Пока такого пути нет, утверждать бесперебойную публикацию с включённой защитой нельзя.
4. Для готового набора правил определить защиту от устаревшей базы (сейчас строгая проверка актуальности в сохранённом правиле выключена), доступные исключения, последствия для действующих процессов и порядок отката. Проверить, какой именно `validate` от GitHub Actions обязателен и что сбой действительно блокирует слияние.
5. Настроить и отдельно испытать разрешённый механизм работы с выбранными запросами Dependabot; исключить неподтверждённые обновления основных версий, пакеты с локальными копиями и изменения workflow до отдельного рассмотрения. Не объявлять автоматизацию действующей до реального проверенного запуска.
6. Только после тестов включить правило, наблюдать прохождение CI, публикацию Pages и задания обновления, проверить сценарий отказа и откат. Без дополнительного доступа к администрированию не изменять настройки репозитория.

## Проверка конкретного события

Откройте GitHub → Actions → нужный запуск. Зелёный результат сборки не доказывает публикацию сайта; состояние Pages и конкретный проверенный коммит следует смотреть отдельно. Ошибка отправки потребует просмотра разрешений, правила, изменений в `main` и наличия публичного артефакта; не копировать в обсуждение секреты или приватную почту. Архив действителен ограниченное время, для восстановления нужно отдельно проверить состав, источники и свежесть данных.

## Дополнительная проверка инфраструктуры

- На момент проверки последний успешный build Pages соответствовал тогдашнему `main`. Это относится только к конкретному наблюдению, а не гарантирует обновление после будущих push. IndexNow ожидает успешного workflow `pages-build-deployment` и отдельно сверяет развёртывание; без сборки Pages уведомление также может не запуститься.
- Наблюдаемые интервалы между последними запусками новостей по расписанию существенно превышали установленный интервал в 30 минут. `active` означает, что workflow не отключён, но не подтверждает своевременную работу расписания. Причина задержек по этим данным не установлена; стабильность сбора необходимо наблюдать отдельно от проверки публикации.
- У двух production workflow общая группа `site-data-updates`. По [правилам concurrency](https://docs.github.com/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs) при стандартной очереди новый ожидающий запуск может отменить предыдущий ожидающий, даже если `cancel-in-progress: false`. Поэтому эта настройка защищает запущенную работу от отмены, но не обещает выполнения каждого ожидающего запуска. Перед изменением модели очереди проверить доступность и пределы очереди и поведение повторных запусков в GitHub.

## Кандидат для исследования: отдельный GitHub App

Для автоматического PR без ручного разрешения каждого запуска CI GitHub рекомендует рассмотреть installation token отдельного GitHub App вместо встроенного токена ([документация](https://docs.github.com/en/actions/concepts/security/github_token)). Это **проектируемый вариант**, не действующая настройка и не гарантия успешной публикации.

- Установка только на этот репозиторий; предполагаемые минимальные права для создания ветки и PR — Contents: read and write, Pull requests: read and write, обязательные служебные Metadata: read. Точные права для последующих действий следует проверить на тестовом сценарии; не запрашивать Administration, Workflows, Secrets или доступ ко всем репозиториям «на всякий случай». Contents: write — существенное право изменять содержимое репозитория, это не доступ только к новостям; сохранение ruleset без bypass принципиально важно. Источники: [доступ приложений](https://docs.github.com/en/enterprise-cloud@latest/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps) и [создание PR](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request).
- Приложение нельзя использовать в качестве обходящего актора. Настройку регистрации, ключа и ограниченного доступа должен контролировать владелец; ключ и токены нельзя присылать в чат, добавлять в репозиторий или выводить в логи. Реализация должна обращаться с кодом PR, выходами сетевых источников и артефактами как с недоверенными; не выполнять их как код в задании, имеющем ключ.
- Сбор и проверка должны быть отделены от привилегированного этапа; перенос данных — строго по утверждённому перечню публичных файлов, с проверкой происхождения, целостности, формата, размера и путей. Нельзя извлекать произвольные пути, symlink или запускать содержимое. Не доверять одному имени PR или ветки при выборе данных для публикации.
- Для каждого типа данных нужны правила повторных запусков и изменений `main`: повторная генерация или безопасный отказ при устаревшем базовом коммите; без перезаписи чужих изменений, force push и потери архивов. Проверять итоговый объединяемый результат, а не только исходную выгрузку. Strict-проверка актуальности базы может вызвать повторные CI и задержки; её включение нужно отдельно испытать.
- Автоматическое слияние пока не включать: сначала убедиться на тестовом PR, что оно действительно ждёт нужный `validate`, а неисполнение/ошибка его блокирует; затем проверить сборку Pages, опубликованное содержимое и IndexNow. Перечень допустимых обновлений Dependabot должен быть отдельно проверен. Откат должен возвращать прежний рабочий путь без отключения проверок и без несанкционированной публикации.

## Подготовка приложения владельцем — ещё не запуск автоматизации

Это регистрация собственной частной интеграции, а не выдача полного доступа Arena. До настройки и проверки будущего workflow ключ создавать и сохранять необязательно. Действия доступны владельцу в настройках своего аккаунта; текущая интеграция не может выполнить их от его имени.

1. Открыть **Settings → Developer settings → GitHub Apps → New GitHub App** в настройках своего аккаунта ([инструкция GitHub](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)). Указать уникальное имя и адрес сайта в поле Homepage URL.
2. Для автономного запуска без входящих вебхуков снять **Webhook → Active**. В разделе доступа к репозиториям выбрать **Contents: Read and write** и **Pull requests: Read and write**; GitHub обычно добавляет **Metadata: Read-only**. Не выбирать Administration, Workflows, Secrets и остальные права без отдельного обоснования.
3. В разделе установки выбрать **Only on this account**, создать приложение, затем **Install App → Only select repositories** и выбрать только репозиторий этого сайта ([установка](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app)). Проверить, что не выбраны все репозитории.
4. Не создавать private key и не вводить его в Actions до появления проверенного сценария и отдельной инструкции. Ключ, токен и другие секреты не отправлять в переписку и не добавлять в Git. Не добавлять приложение в обход правил. При необходимости доступ можно отменить удалением установки приложения.

Запись приложения и его установка сами по себе не запускают CI, не создают PR, не активируют защиту и не настраивают автослияние. После них всё ещё необходимы код с минимальным доступом, тест без публикации, проверка защит и Pages, и только затем поэтапное включение.

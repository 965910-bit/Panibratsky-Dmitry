# Автоматизация Яндекс Вебмастера и Google Search Console

## Что подготовлено

`scripts/webmaster_readonly.py` — первый программный компонент, а не готовая служба. Он может получить снимок для `https://scm-news.ru/` из официальных API обоих сервисов при передаче краткоживущих токенов в окружении процесса. Используются только GET и один POST Google `searchAnalytics.query` для получения данных; операции изменения свойств и Sitemap не вызываются. Секреты не передаются в командной строке и не выводятся программой. Вывод содержит данные кабинетов и может быть приватным: не публиковать отчёты, токены и клиентские файлы в Git, Actions или чат. Не давать токены автору инструмента.

Google: поиск доступного свойства `https://scm-news.ru/` либо `sc-domain:scm-news.ru`, данные о целевом Sitemap и агрегаты web-поиска за выбранный период с задержкой пять дней (`dataState=final`). При наличии обоих свойств выбирается URL-префикс; данные свойств различаются. Пустой ответ не трактуется как ноль. Проверка URL, ошибки обхода, полная индексация, сравнение периодов и аудит контента не реализованы.

Яндекс: получение идентификатора владельца, выбор точного HTTPS-хоста и проверка подтверждения прав, поиск целевого Sitemap среди первых 100 добавленных пользователем, суточные показатели показов и кликов для всех типов устройств. Наличие Sitemap в списке **не доказывает** его успешной обработки; отрицательный результат при общем числе более 100 требует отдельной проверки. Отсутствующий показатель — не ноль. Яндекс и Google не следует складывать или сравнивать без учёта методик, периодов и свойств.

По умолчанию 28 дней, 5 дней отступ от текущей локальной даты. Задержка данных у поставщика может быть больше. Результат фиксирует время формирования UTC, период, идентификатор свойства и статус каждого источника: `ok`, `error`, `not_connected`. При отсутствии хотя бы одного источника возвращается ненулевой код. Ошибки одного источника не превращаются в нули и не скрывают второй. Сетевой ответ ограничен, редиректы выключены, тело ошибок поставщиков не печатается.

## Ограничения и дальнейшие шаги

- **Ни один кабинет не подключён, реальных данных и токенов нет; интеграция на Windows и с реальными API не проверялась.** Тесты используют искусственные ответы.
- Автоматическое создание разрешений, безопасное хранение и обновление токенов, установщик Windows, расписание и отправка уведомлений пока не реализованы. Временный токен сам по себе не обеспечивает работу 24/7. Не просить пользователя вставлять токены в чат или записывать их в репозиторий.
- Google требует зарегистрировать OAuth-приложение в Google Cloud, активировать Search Console API, и выдать `webmasters.readonly`; возможность использовать созданный проект, лимиты, экран согласия и время жизни авторизации требуют проверки. Яндекс требует приложения OAuth и соответствующих разрешений API; серверные права могут быть шире набора операций, используемых программой. Только после выбора способа подключения готовить безопасный установщик и проверять на тестовом аккаунте с владельцем.
- GitHub workflow `Daily public SEO smoke check` ежедневно по расписанию проверяет публичные страницы и не обращается к кабинетам. Его успешный результат не доказывает индексацию или доставку оповещений.
- Без доступа к кабинету нельзя утверждать, что право владения подтверждено, карта обработана или данные актуальны. Внешние сервисы могут менять интерфейсы, требования и квоты.

## Тестирование без учётных данных

`python3 -m unittest discover -s tests -p 'test_webmaster_readonly.py' -v` запускает локальные тесты с поддельными ответами; сетевые запросы к сервисам в них не выполняются. Запуск `python3 scripts/webmaster_readonly.py` без токенов сообщает `not_connected` и завершится с кодом 1 — это ожидаемое состояние, а не нулевая статистика.

## Подготовка реальных действий

`scripts/webmaster_actions.py` добавляет отдельный компонент отправки. По умолчанию — план без изменений; режим `--apply` разрешает действия после проверки опубликованного sitemap, точного совпадения байтов выбранных страниц, canonical и noindex через тот же preflight, что и IndexNow. Без токенов программа не отправляет запросов и возвращает ненулевой код. Токены берутся только из переменных окружения процесса и не печатаются. Google отправляет только отсутствующий `https://scm-news.ru/sitemap.xml` в выбранное точное свойство; Яндекс — только отсутствующую карту для подтверждённого HTTPS-хоста. Если список карт Яндекса неполный и нужная карта не найдена, запись блокируется.

Для Яндекса можно передать до пяти разных `--url` из текущего списка PAGES. Перед отправкой проверяется остаток квоты; случаи подтверждённого дубля 409 и исчерпания квоты 429 распознаются по кодам API. Только ответ с идентификатором задачи называется принятым. Это не означает успешный обход или индексацию. Проверки статуса задач и устойчивого журнала отправок пока нет; запуск после неопределённой сетевой ошибки не следует автоматически повторять до сверки в кабинете. Код не выбирает изменённые страницы самостоятельно и не содержит автозапуска после деплоя. Прежний IndexNow — отдельный, уже настроенный процесс.

Для включения нужны OAuth-приложения и соответствующие права: Google требует `webmasters` для отправки Sitemap, что шире `webmasters.readonly`; право на токене может позволять и иные операции, хотя код их не выполняет. Яндекс требует соответствующие права API. **Сейчас разрешения, безопасное хранение/обновление токенов, подключение и планировщик не настроены; никакие действия в кабинетах этим изменением не выполнены.** Тесты используют поддельные API, на реальных сервисах и Windows работа не проверена. Не вводите токены в чат, аргументы команд или публичный Git. Изменять доступы, удалять сайты и карты программа не умеет.

Источники: https://developers.google.com/webmaster-tools/v1/sitemaps/submit ; https://yandex.ru/dev/webmaster/doc/en/reference/host-user-added-sitemaps-post ; https://yandex.ru/dev/webmaster/doc/en/reference/host-recrawl-post ; https://yandex.ru/dev/webmaster/doc/en/reference/host-recrawl-quota-get . Google Indexing API ограничен определёнными типами страниц; программа не вызывает его для обычных статей.

## Подготовленный запуск после публикации

В `.github/workflows/webmaster-after-pages.yml` подготовлен запуск после успешного GitHub Pages на `main`. По умолчанию отключён: без переменной репозитория `SCM_WEBMASTER_AUTOMATION=1` запросы в кабинеты не выполняются. Скрипт `scripts/webmaster_after_deploy.py` проверяет тип и результат события, текущий `main`, наличие предыдущей успешной публикации и родство коммитов, вычисляет изменённые HTML из существующего sitemap-allowlist и проверяет опубликованные байты, sitemap, canonical и noindex. После повторной проверки текущего `main` вызывает подготовленные действия. Проверка не атомарна с деплоем: при одновременной смене main после последней проверки гонку полностью исключить нельзя.

Запуск выполняется в GitHub Actions, не на домашнем ПК. Для реального включения потребуются отдельно созданные и выданные владельцем доступы, защищённое хранение и настройка GitHub: `SCM_WM_GOOGLE_CLIENT_ID`, `SCM_WM_GOOGLE_CLIENT_SECRET`, `SCM_WM_GOOGLE_REFRESH_TOKEN` и `SCM_WM_YANDEX_ACCESS_TOKEN` в Secrets, затем переменная включения. Значения не указывать в исходниках, логах или чате. Скрипт обновляет короткоживущий токен Google через официальный OAuth endpoint; отозванные или истёкшие разрешения вызывают ошибку. Для внешнего OAuth-проекта Google в статусе Testing срок refresh-токена может составлять семь дней: https://developers.google.com/identity/protocols/oauth2 . Токен Яндекса хранится как выданный access token, автоматическое продление/ротация Яндекса **не реализованы**; при истечении понадобится повторная настройка. Нельзя утверждать непрерывную работу без неё. Регистрация приложений и получение прав не выполнены; реальный запуск, доступ и уведомления не проверены.

На переобход Яндекса передаётся не более пяти изменённых страниц за запуск с учётом квоты; остальные URL отображаются в результате и дают ошибочный статус. **Постоянной очереди, автоматического восстановления отложенных URL и уведомления в Telegram пока нет**. Ошибки при частично выполненных действиях могут оставить неопределённый результат; автоматические повторы не настроены, повторные запуски workflow и событий Pages с `run_attempt` не равным единице блокируются. Повторная новая публикация или запуск вне workflow не гарантирует дедупликацию: перед восстановлением требуется сверка с кабинетом. Успешный приём не подтверждает индексацию. Не следует включать автоматизацию до проверки полномочий, секретов и поведения в реальных сервисах.

## Подготовка подключения Google без пересылки токенов

`scripts/webmaster_google_connect.py` — подготовленный локальный помощник для Google Desktop OAuth. После явного согласия он открывает официальный браузерный вход; callback слушает только `127.0.0.1`, проверяет случайный state и использует PKCE S256. Код и токены не выводятся; токен обмена передаётся GitHub CLI через stdin, без аргументов команд. Данные не записываются программой на диск. Запрашивается широкий `webmasters`, так как он необходим для отправки sitemap, а не только просмотра. Это право потенциально позволяет другие изменения через API, хотя подготовленная автоматизация ограничена описанными операциями.

Для использования в дальнейшем потребуются поддерживаемый Python, GitHub CLI с доступом к секретам именно этого репозитория, а также созданный владельцем Google Cloud проект с включённым Search Console API и скачанный JSON OAuth-клиента типа Desktop. JSON содержит данные клиента и должен оставаться приватным вне репозитория. Вызов локально: `python scripts/webmaster_google_connect.py "ПУТЬ_К_DESKTOP_OAUTH_JSON"`. После согласия помощник проверяет список существующих секретов репозитория, отказывается от преднамеренной перезаписи найденных имён, затем сохраняет три значения через `gh secret set`; все три операции не являются транзакцией, возможны частичные записи при сбое и гонки с другими администраторами. Проверить/удалить частично созданные записи можно только в настройках GitHub, не раскрывая их значения. Скрипт **не включает** workflow и не проверяет реальные права на свойство. Отзыв разрешения у Google или удаление секретов отключит доступ. Само наличие секретов не включает отправку: переменная `SCM_WEBMASTER_AUTOMATION` не меняется.

Это подготовка, не фактически выполненное подключение: вход пользователя, создание приложения Google и проверка реального OAuth/Windows/GitHub не проводились. В Google OAuth-проекте Testing refresh-токен может истечь через семь дней; повторная авторизация и правила производства требуют отдельного решения. Подключение Яндекса, безопасная ротация его refresh-токена и очередь отложенных страниц остаются неготовыми. Документация: https://developers.google.com/identity/protocols/oauth2/native-app и https://developers.google.com/webmaster-tools/v1/how-tos/authorizing .

## Подготовка подключения Яндекса

`scripts/webmaster_yandex_connect.py` — локальный помощник с device-flow Яндекс OAuth. Он запрашивает `webmaster:hostinfo` и `webmaster:verify`: эти разрешения могут позволять изменения и управление сайтом, хотя действия проекта ограничены отправкой sitemap и переобходом. После согласия пользователя помощник показывает одноразовый код локально и открывает строго фиксированный официальный адрес `https://oauth.yandex.ru/device`. Код вводится только там, не в чате. Приложение соблюдает интервал запросов и останавливается при ошибке/истечении кода.

Токен не выводится, а после чтения списка хостов сохраняется через GitHub CLI stdin в `SCM_WM_YANDEX_ACCESS_TOKEN`, только если найден ровно один подтверждённый `https://scm-news.ru/`. Существующий секрет помощник не перезаписывает намеренно; возможна гонка с другим администратором или неопределённый исход записи при сетевом сбое. OAuth-секрет приложения вводится скрыто локально, пароль Яндекс ID программе не нужен. Ни токен, ни секрет приложения не записываются этой программой в файл; данные хранятся в памяти текущего процесса и могут быть доступны вредоносному ПО или администратору. Вебмастер API и GitHub получают необходимые данные для работы. Обновление токена и безопасная ротация не реализованы: при истечении понадобится контролируемое переподключение. Проверка наличия права на запись и фактической операции, модерация приложения и реальная работа на Windows не проводились.

До использования владелец должен зарегистрировать своё приложение Яндекс OAuth с нужными правами и возможностью device-flow, использовать авторизованный `gh` с правом изменения секретов нужного репозитория и запустить `python scripts/webmaster_yandex_connect.py` на своём компьютере. Может потребоваться одобрение приложения Яндексом. Помощник не создаёт приложение и не включает workflow. Запуск после истечения токена с уже существующим секретом остановится: для замены потребуется отдельная проверенная процедура, которой пока нет. Никаких реальных подключений и секретов в этой работе не создавалось. Источник: https://yandex.ru/dev/id/doc/en/codes/screen-code-oauth .

## Основа устойчивой очереди переобхода

`scripts/webmaster_queue.py` содержит локальные примитивы SQLite: сохранение разрешённых canonical URL и ревизии, атомарный захват по одному URL, фиксацию принятия/квоты/неизвестного исхода и ручное разрешение неопределённости. Более новая запись, добавленная пока запрос выполняется, остаётся в очереди. При повторной постановке того же URL и ревизии выполненное действие не повторяется. После аварии незавершённое действие надо помечать как неопределённое **только после остановки единственного исполнителя**; повтор без проверки кабинета опасен. Принятие задачи не означает обход или индексацию.

Это пока **не включённая автоматизация**: очередь не подключена к workflow, не вызывает Яндекс и не отслеживает завершение обхода. GitHub runner временный, поэтому SQLite-файл на нём не является постоянным хранилищем. Для рабочего запуска ещё нужны надёжное постоянное хранилище с ограниченным доступом и резервным копированием, сериализация публикаций и работников, обработка устаревших событий (enqueue предполагает порядок ревизий), проверка актуального опубликованного содержимого перед каждой отправкой, согласование неизвестных исходов и расписание/уведомления. Нельзя использовать артефакт с истекающим сроком или кэш как гарантию сохранности очереди. Примитивы не заменяют контроль прав и квот API и не доказывают успешную работу на GitHub Actions.

`scripts/webmaster_queue_worker.py` добавляет тестируемый исполнитель для этой очереди: за вызов до пяти URL, по одному за запрос, проверка опубликованных байтов и canonical перед отправкой, остановка при квоте или неопределённом результате. Неопределённый или незавершённый запрос блокирует выдачу следующих задач до сверки; непрошедшая проверку публикации задача возвращается в ожидание. Сбой сохранения после возможной отправки остаётся незавершённым и не считается успехом. Отдельно надо учитывать возможную отправку sitemap, которую выполняет используемая операция Яндекса. Состояние `already_added` подтверждает лишь ответ сервиса, а не факт обхода или индексации.

Исполнитель — программный примитив, **не подключён к workflow или расписанию** и не имеет CLI. Вызывающий код должен гарантировать единственного исполнителя, актуальный и успешно опубликованный checkout, порядок событий и постоянную локальную базу; отметка ревизии в очереди служит идентификатором поколения, а проверяются актуальные файлы checkout. Автоматического восстановления после аварии, безопасной ротации токена, оповещений и проверки итогов обхода пока нет. Модуль и его тесты не выполняли реальных вызовов API.

## Проверка результатов переобхода

При сохранении подтверждённого принятия новая таблица SQLite записывает идентификатор задачи, URL и ревизию атомарно вместе с состоянием очереди; история не теряется при новой отправке того же URL. При первом открытии старой базы восстанавливается только последний сохранённый в ней task_id, если он ещё присутствует: ранее утраченные идентификаторы восстановить невозможно. Дублирующийся task_id с другим URL или ревизией блокирует фиксацию и оставляет запрос незавершённым.

`scripts/webmaster_recrawl_status.py` — ограниченный по числу запросов (по умолчанию 20, не более 50) read-only примитив опроса точных task_id подтверждённого сайта. Он проверяет соответствие task_id и URL ответа, сохраняет `IN_PROGRESS`, `DONE` или `FAILED`; ошибку сети, неизвестный ответ или отсутствующую задачу показывает как `UNKNOWN`, не приравнивая к неудаче обхода. `DONE` означает обход роботом, **не индексацию**. При `FAILED` автоматическая повторная отправка не выполняется: требуется диагностика доступности. Очередь выбирает для следующей проверки прежде не проверявшиеся, затем давно проверенные незавершённые задачи. У задач `already_added` и неоднозначных исходов надёжного task_id нет, этот опрос их не разрешает.

Этот код не запускается по расписанию, не включён в workflow, не уведомляет и не делает настоящих запросов без вызывающей программы и токена. Для практической работы по-прежнему требуются постоянная база, подключённый кабинет, планировщик, безопасная ротация токена и оповещения. Документация Яндекса: https://yandex.ru/dev/webmaster/doc/en/reference/host-recrawl-task-get .

## Ограниченные повторы безопасного чтения API

Общий API-клиент действий и проверки задач повторяет только `GET` без тела при временных сетевых ошибках и HTTP 429/500/502/503/504: максимум три попытки, интервалы 1 и 2 секунды. Числовой `Retry-After` до 5 секунд соблюдается; при большем значении, HTTP-date или неверном заголовке немедленный повтор не выполняется. Ошибки прав, неверные ответы и прочие коды не повторяются. `POST` и `PUT` никогда не повторяются автоматически этим механизмом, даже после таймаута или ошибки сервера: их исход может быть неизвестен. Настройки применяются только в использующих этот клиент функциях; получение Google OAuth-токена, публичная проверка сайта и GitHub API не покрываются. Протестировано на имитациях, не на подключённых кабинетах.

## Отчёт при частичной отправке после публикации

Подготовленный workflow после Pages теперь вызывает действие Яндекса по одному URL, сохраняя в отчёте уже полученные результаты, даже если последующая отправка прервётся. Текущий URL при ошибке помечается `unknown`, а ещё не начатые URL выводятся в `deferred_urls`; при исчерпании квоты следующие URL не отправляются. Перед каждым вызовом дополнительно проверяется, что `main` ещё соответствует развернутой ревизии. Эта проверка сокращает, но не устраняет гонку между чтением `main` и внешним запросом. Каждый вызов заново проверяет сайт, sitemap и квоту, что увеличивает число GET-запросов. При неподключённом Яндексе все изменённые URL также отображаются как отложенные.

Результаты остаются в журнале workflow, а не в постоянной очереди: это не автоматически возобновляемая обработка. Заявку с неизвестным результатом нельзя повторять без сверки кабинета. Неизвестный исход может затронуть и добавление sitemap, даже если в отчёте нет подтверждения. Перезапуск workflow по-прежнему блокируется; история в журнале ограничена сроком хранения GitHub. Действия по умолчанию отключены, реальные запросы при тестировании не выполнялись.

## Курсор публикаций и краткий отчёт

Локальная очередь SQLite дополнена атомарным курсором: постановка изменённых canonical URL и продвижение курсора происходят в одной транзакции. При повторном событии очередь не дублируется, устаревшая ревизия не перезаписывает более новую, расхождение истории и ошибки чтения Git останавливают продвижение. Для первого запуска обязательна явно выбранная базовая ревизия; используемые адаптеры сравнивают неизменяемые SHA. Вызывающий код обязан отдельно убедиться, что целевая ревизия — актуальный main и успешно опубликована; прямой `enqueue` нельзя смешивать с курсором как упорядоченный источник. Удалённые и исключённые из sitemap страницы на переобход не ставятся. Компонент не подключён к GitHub Actions, постоянное хранилище и планировщик отсутствуют.

Workflow после Pages теперь формирует краткое резюме в GitHub Actions: отдельно показывает выключенный процесс, отсутствие подключения, принятые/неопределённые запросы и число неотправленных страниц. Резюме не является уведомлением вне GitHub, не заменяет постоянную очередь и не гарантирует индексацию. Уведомления по почте отложены; существующий Telegram digest предназначен для новостей и не используется для отправки административных отчётов в этот канал.


## Ежедневная публичная проверка

Публичный SEO smoke переведён с еженедельного расписания на ежедневное около 08:41 UTC. Он выполняет по одному запросу к каждой странице из текущего списка sitemap, а также к sitemap и robots; на текущем списке это 39 запросов в день при одном запуске, дополнительные ручные запуски добавляют запросы. Тайм-аут workflow составляет 35 минут, чтобы последовательные сетевые ожидания и ограниченные повторы не прерывали отчёт преждевременно. Это только проверка публичных ответов и заданных технических признаков, не подключение Вебмастеров и не оценка индексации. Расписание GitHub может задерживаться или пропускаться; внешние уведомления не настроены, и единичный сетевой сбой может выглядеть как замечание.

## Оповещения публичной проверки в GitHub Issues

При ошибке ежедневного публичного smoke workflow пытается открыть одну общую публичную задачу в Issues с фиксированным названием и ссылкой на запуск; содержимое отчёта, токены и данные аккаунтов туда не копируются. Пока такая задача открыта, повторная ошибка новую задачу не создаёт. После следующего успешного smoke бот закрывает только собственную задачу с точным шаблоном; чужие и изменённые задачи не трогает. При отмене или неопределённом исходе проверки действий с задачами нет. Автоматическое закрытие означает лишь, что этот ограниченный smoke снова прошёл, а не что индексирование исправлено. В задачи нельзя включать приватные данные. Уведомления пользователю зависят от его подписок и настроек GitHub, их доставка не гарантирована.

Workflow получил `issues: write` помимо `contents: read`; они действуют только в этом workflow. Перед изменением проверяется неизменяемый ID репозитория и принадлежность задачи GitHub Actions bot. При нескольких похожих бот-задачах, неполном перечне открытых задач или ошибке прав процесс прекращается без мутации; при ошибке записи GitHub её исход может быть неизвестен, вслепую запрос не повторяется. Отказ уведомления отмечается ошибкой workflow. Сбои до загрузки скрипта или недоступность самого GitHub могут помешать созданию задачи. Реальное создание и закрытие тестируются только имитациями; права и поведение GitHub в рабочем запуске необходимо отдельно подтвердить. Почта и канал новостей Telegram не используются.


Публичный smoke отдельно отмечает очевидную группу `User-agent: *` с `Disallow: /` без непустого `Allow` в той же группе. Это сигнал о проблеме общего правила, а не полный разбор robots.txt: отдельные группы конкретных роботов и сложный приоритет правил требуют дополнительной проверки. При сетевой ошибке или HTTP 500/502/503/504 публичный GET повторяется один раз через 2 секунды; при `Retry-After`, 429, редиректах и прочих HTTP-кодах повтора нет. В худшем случае вместо 39 может быть до 78 запросов за запуск; повтор не относится к изменяющим API-запросам.


Для запросов к `oauth.yandex.ru` помощник передаёт права через пробел согласно русской документации device-flow: https://yandex.ru/dev/id/doc/ru/codes/screen-code-oauth . Английская редакция на момент проверки указывает запятые; совместимость с реальным приложением для доступа к API ещё не подтверждена и при отказе нужно остановиться, не обходить проверку прав.

### Альтернативный способ подключения Яндекса

После неудачного запуска device-flow до выдачи кода устройства подготовлен `scripts/webmaster_yandex_code_connect.py`: открывает официальный `oauth.yandex.ru/authorize`, использует `response_type=code`, фиксированный `verification_code` redirect, PKCE S256 и необходимые права, принимает показанный Яндексом код только локально, обменивает его без client secret, проверяет подтверждённый сайт и передаёт токен в GitHub CLI через stdin. Исходная ошибка скрывала подробности, поэтому её причина неизвестна; утверждать несовместимость device-flow нельзя. GitHub secret не перезаписывается намеренно; запись не атомарна с сетевым ответом. При наличии ошибки отображаются только безопасные известные коды OAuth, без ответа сервера и секретов.

Вариант 2 распространяется в `downloads/SCM-Yandex-Webmaster-connect-v2.zip`, проверен на имитациях и на соответствие включённых исходников, но реальный OAuth, права на действия и Windows ещё не подтверждены. Включение workflow и автоматическое обновление Яндекс-токена не выполняются. Источник: https://yandex.ru/dev/id/doc/ru/codes/screen-code .

## Ручная проверка подключённого Яндекс Вебмастера

`Yandex Webmaster connection check` запускается вручную только на `main`, использует `SCM_WM_YANDEX_ACCESS_TOKEN` и только GET: проверяет подтверждённый точный сайт, наличие sitemap в полном списке добавленных карт (при неполном списке останавливается) и оставшуюся квоту переобхода. В журнал выводятся только эти агрегированные результаты; токен, ID аккаунта и полные данные ответов не выводятся. Workflow не отправляет карты или URL и не доказывает наличия прав на запись, завершения обработки или индексации. Ошибка не доказывает причину; автоматизация остаётся выключенной.

### Однократная сверка карты в подключённом Яндексе

`Yandex sitemap reconciliation` — ручной запуск на `main`: сверяет проверенный checkout с текущим main и последней успешно собранной версией Pages, проверяет живую sitemap и контрольный файл, затем использует точный подтверждённый хост. Если в полном полученном списке карты нет, отправляет только `https://scm-news.ru/sitemap.xml`; если она уже добавлена, ничего не меняет. Страницы на переобход этот запуск не отправляет. Повторный attempt GitHub заблокирован; при неоднозначном ответе нельзя запускать повтор вслепую. Состояние в стандартном уведомлении (`submitted`/`already_present`) не означает успешной обработки карты или индексации. Проверка main и внешняя операция не атомарны, поэтому одновременное обновление main между ними остаётся риском. Автоматическую очередь или продление токена этот запуск не включает.

После неуспешной попытки однократной сверки карты повтор автоматически не выполняется. Диагностический workflow дополнен только чтением: сообщает в аннотации наличие карты и квоту и отдельно проверяет условия публикации без обращения к изменяющим API Яндекса. Это позволяет сверить состояние после возможного частичного действия; повтор возможен только после оценки результата, а не по одному факту ошибки.

После первой неуспешной реальной сверки read-only запуск подтвердил отсутствие карты в списке и остаток квоты 50 на момент проверки; независимый production preflight прошёл. Повторная сверка также закончилась ошибкой, её исход необходимо повторно проверить чтением. Для дальнейшей диагностики сверка выдаёт только названия этапов и безопасные HTTP-статусы/известные коды API; тела ответа, URL с параметрами и секреты не выводятся. Сам по себе статус ошибки не устанавливает причину или факт записи.

Ручной запуск `46076138258` вернул HTTP 504 на общем этапе обращения к Яндексу: старый журнал не определяет, был ли это GET или POST. Последующее чтение `46076187717` не нашло карту в полном списке; отсутствие в списке не доказывает, что запрос с неопределённым исходом не обрабатывается с задержкой. Новая диагностика различает фиксированными метками чтение пользователя, хостов, списка и отправку, не раскрывая адреса API и секреты; её наличие не означает, что предыдущий запрос идентифицирован. Автоматического повтора по 504 нет. Успешный ответ добавления теперь обязан содержать непустой `sitemap_id` (формат по документации Яндекса); иначе результат остаётся неопределённым. https://yandex.ru/dev/webmaster/doc/en/reference/host-user-added-sitemaps-post

Ежедневный workflow `webmaster-yandex-monitor.yml` (примерно 09:23 UTC и вручную) только читает состояние подтверждённого сайта, список добавленных карт и остаток квоты. При ошибке чтения создаёт отдельный GitHub Issue от бота; закрывает только свой неизменённый Issue после восстановления чтения. Отсутствие карты само по себе не считается ошибкой доступа: её проблема отслеживается отдельно в Issue #225. Если недоступен сам GitHub API или не хватает прав Issues, запуск завершится ошибкой, но создать уведомление может не получиться; доставка уведомлений зависит от подписки GitHub. Мониторинг не отправляет sitemap или запросы переобхода, не подтверждает индексацию и не обновляет токен.

Монитор отдельно читает список sitemap, обнаруженных роботом (`GET /sitemaps`): наличие и источники, число URL и ошибок, факт указанной даты последнего обращения. Это иной список, чем `user-added-sitemaps`. Запрашивается только первая страница (до 100), поэтому отсутствие в ней не считается доказательством общего отсутствия. Обнаружение/обработка карты не гарантирует индексацию. Формат: https://yandex.ru/dev/webmaster/doc/en/reference/host-sitemaps-get

Запуск `46092572274`: робот Яндекса обнаружил sitemap через `ROBOTS_TXT`, сообщает 16 URL и одну ошибку; список добавленных пользователем при этом не содержит карту. Эти показатели относятся к последнему чтению робота и не устанавливают причину ошибки или текущую индексацию. Для уточнения монитор выводит только безопасную дату последнего чтения и фиксированные статусы известных проблем через GET диагностики сайта; `UNDEFINED` и отсутствующие статусы не считаются отсутствием проблемы. https://yandex.ru/dev/webmaster/doc/en/reference/host-diagnostics-get

Дополнительно монитор заводит отдельные bot-owned Issues для подтверждённых ошибок sitemap и замечания Яндекса об описаниях. Проверки и закрытие — раздельные: неизвестный статус, отсутствие карты на первой странице либо отсутствие корректной даты чтения не считается восстановлением. Состояние относится к последним сведениям Яндекса, а не обязательно к текущему сайту. Доставка уведомлений зависит от GitHub. Тест CI требует единственное непустое уникальное meta description в head каждой страницы текущего sitemap; это не гарантирует индексирование и не проверяет все страницы вне карты.

Дополнительная публичная ежедневная SEO-проверка проверяет на реально опубликованных страницах из sitemap по одному непустому, неповторяющемуся meta description в head. Она не подтверждает то, что Яндекс уже переобошёл страницы; после исправления опубликованной страницы замечание Яндекса может сохраняться до пересмотра его данных.

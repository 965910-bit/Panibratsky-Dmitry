# Готовность Telegram: контрольный список перед изолированным тестом

Локальный обзор конфигурации и документации, ноябрь 2026. Это **не** подтверждение текущего состояния удалённых систем: новый сквозной тест, миграция, развёртывание, отправка и изменение расписания в рамках этого обзора не выполнялись. Рабочий канал использовать нельзя до отдельной проверки и решения владельца. Публикация — только по личному одобрению.

## Что имеется

- Отдельные тестовые бот, канал и staging Worker были согласованы ранее. Ранее тестовый бот доставлял сообщения в личный чат; это не проверка новой версии или всей цепочки. Не считать загруженную версию активной без проверки.
- `telegram_review_staging.yml` запускается вручную в окружении `STAGING`; при выполнении может отправить максимум один черновик тестовому рецензенту. Это не расписание и не разрешение на автоматическую публикацию.
- Галерея неподтверждённых кандидатов готовится отдельно без секретов и без отправки в Telegram. Успешный артефакт не означает, что кандидаты есть или что их факты, права и уникальность проверены. По последнему локальному снимку ленты от 17 ноября автоматический отбор дал 0 из 2055 записей; это не гарантия для другого дня.
- Новая защита одной очереди, `/intake-one`, миграция и ручная сверка `/reconcile` проверены локально, но не испытаны на настоящей D1 вместе с Telegram. Состояния `sending` и `notifying` требуют человеческой сверки; ошибка сети не доказывает отсутствия отправки. Старую прямую рассылку `send_telegram.yml` не включать.

## Условия перед тестом

1. Сверить текущую активную версию и привязки **тестового** Worker, D1, бота, личного чата и отдельного тестового канала, не раскрывая секреты; проверить настройки доступа, webhook и актуальное состояние очереди. Не менять рабочие ресурсы. При неопределённости остановиться.
2. До изменений D1 согласовать план, сделать и проверить резервную копию, изучить совместимость миграции и возможность восстановления; отдельно согласовать развёртывание новой версии. Процедура и ограничения — `telegram-review/README.md`. Не применять миграцию и не переключать webhook без такой сверки.
3. Для реального материала проверить применимость условий источника, права на текст/изображения, фактологию, актуальность и уникальность, добавить собственный вывод. ATI и «Логистика 360» исключены из автоматического отбора до уточнения условий. Если пригодного материала нет — честно остановиться, не заполнять очередь искусственно.
4. На изолированном контуре отдельно согласовать сквозной тест одного **синтетического** черновика: доставка в личный тестовый чат, отсутствие публикации до явного одобрения, одобрение в тестовый канал, отклонение другого черновика и проверка отсутствия публикации. Проверить повторные нажатия, параллельную подачу, блокировку ожидающей очереди, журнал и поведение при неопределённом ответе. Синтетические материалы не публиковать в основной канал.
5. При зависшем или неопределённом состоянии сначала сверить сообщения и запись с ответственным человеком; не повторять отправку и не редактировать базу вручную наугад. `/reconcile` меняет только подтверждённые неопределённые состояния и не гарантирует exactly-once: выполнять по README и только после проверки фактического результата.
6. После успешного теста и оценки прав отдельно согласовать режим подготовки и личного уведомления, ограничения частоты, обработку пустого списка, мониторинг и откат. Расписание автоматической подачи в очередь отсутствует. До него нельзя обещать ежедневную доставку; даже расписание не гарантирует кандидатов или запуска.

Операционные детали, команды и актуальные ограничения находятся в `telegram-review/README.md`; этот список не заменяет runbook и не разрешает выполнение опасных действий.

Из той же документации следует уточнение среды, важное для изоляции: журнал «2 отправленных / 2 отклонённых» относится к рабочему Worker `scm-telegram-review` (база `scm-review`; на момент той проверки активной была версия `c72a64b8`), где выполнялись `gallery-submit --send` → `/intake` → личный чат → отклонение. Следовательно, прошлые проверки личного согласования выполнялись рабочим Worker в личный чат, а не staging-контуром; сквозного теста staging с настоящим Telegram до сих пор не было. Если бы бота обслуживал staging Worker, `/status` показал бы нули по пустой staging-базе. Это вывод из документации и показанных экранов, а не проверка текущего webhook или значений секретов: состояние с тех пор могло измениться.

Следствие: для сквозного теста staging не хватает одной связи — настоящего тестового токена в секретах staging (вместо заглушки) и бота, чей webhook указывает на подтверждённый адрес `https://scm-telegram-review-staging.965910.workers.dev/telegram`. Остальное подготовлено: миграция 002 выполнена в тестовой D1, версия `e2998d26` загружена и ждёт отдельного решения об активации, код проверен локально. Возможные пути — отдельный новый бот (рабочий Worker и текущий тестовый бот не затрагиваются) или переключение webhook существующего бота с планом возврата (рабочий Worker на время теста перестанет получать его обновления). Выбор за владельцем; до решения ресурсы не менялись, PR из этого изменения не создаётся без отдельной просьбы.

## Согласованный путь без создания новых ресурсов (18 ноября 2026)

Владелец отказался от создания новых бота или канала: все ресурсы уже есть. Согласован план переподключения существующего бота `scm_gerasimov_review_bot` к staging без создания чего-либо нового; выполнение не начато, ресурсы не изменялись. Порядок шагов важен: сначала активация версии, затем секреты, затем webhook — иначе активация `e2998d26` вернёт заглушку токена (значения секретов хранятся вместе с версией).

1. Сохранить текущий webhook бота через `getWebhookInfo` (адрес рабочего Worker для отката; значение рабочего `WEBHOOK_SECRET` из сохранённых владельцем записей понадобится при откате).
2. Активировать `e2998d26` в Deployments staging Worker — то отдельное согласованное решение об активации, которое ранее откладывалось.
3. В секретах staging заменить `BOT_TOKEN` на настоящий токен существующего бота и убедиться, что `REVIEWER_ID` = личный Telegram ID владельца; `CHANNEL_ID` на время теста = тот же личный ID, тогда «публикация» придёт в личный чат и ни один канал не затрагивается. `WEBHOOK_SECRET` и `INTAKE_SECRET` staging не менять. Каждое изменение секрета создаёт новую версию с тем же кодом — активный ID версии изменится, это ожидаемо.
4. Переключить webhook бота на подтверждённый адрес `https://scm-telegram-review-staging.965910.workers.dev/telegram` с тестовым значением `WEBHOOK_SECRET` staging; для отката — одна команда `setWebhook` на адрес из шага 1.
5. Проверить связку `/status` (ожидание всех нулей по пустой staging-базе), затем два синтетических `/draft` с разными URL: одобрение → пост в личный чат и `sent` в журнале; отклонение → без публикации и `rejected`. Публикации до нажатия кнопки быть не должно.
6. После теста вернуть webhook рабочему Worker. Пока webhook на staging, рабочий Worker не получает обновления бота; его расписание выключено, поэтому окно переключения безвредно. Рабочий Worker, база `scm-review`, секреты production и основной канал не затрагиваются.

Бэклог улучшений от агента (предложения, ничего не реализовано, каждое требует отдельного согласования): после staging-теста — перенос на production и подключение канала последним шагом; улучшение отбора кандидатов (сейчас 0 из 2055 на снимке: расширить и освежить источники, пересмотреть пороги, права по каждому источнику); миграция 003 с рубрикой/хэштегами черновика для навигации в канале и ленте; брендинг PNG-карточек в `card.py`; авто-черновик «итоги недели» для личного одобрения; указание адресата публикации в префиксе review-сообщения.

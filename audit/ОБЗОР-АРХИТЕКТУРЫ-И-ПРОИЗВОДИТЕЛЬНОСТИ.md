# Обзор репозитория, архитектуры и приоритетов улучшения

## Краткий вывод

Сайту не требуется срочная смена языка или полный переписанный сайт. Статические HTML, CSS и JavaScript подходят для портфолио и SEO; Python подходит для сборщиков и проверок; Node.js и JavaScript — для серверного API, тестов и Cloudflare Worker; SQL — для D1. Самый заметный потенциал сейчас — безопасность рабочих панелей, корректный запуск аналитики и оптимизация конкретных тяжёлых ресурсов, а не массовый переход на React, TypeScript или другой язык. Перевод сам по себе не гарантирует ускорения, индексации или новых обращений.

## Объём и ограничения

- Снимок активной ветки `3c5dfbfd`; это не обязательное состояние опубликованного `main`. Учтены все 461 отслеживаемых Git файлов, приблизительно 43,96 МБ без `.git` и зависимостей. Не анализировались скрытые от Git пользовательские файлы, прежние версии Git, production D1 и содержимое закрытых кабинетов.
- Пофайловая таблица: `ИНВЕНТАРЬ-ФАЙЛОВ-АРХИТЕКТУРЫ.md`. Она содержит автоматическую классификацию и применимые синтаксические проверки каждого файла, но не утверждает, что каждую строку каждого файла вручную изучил эксперт или что каждый бинарный файл проверен на содержание, авторские права и безопасность.
- Проверены Python AST, синтаксис JS/JSON/XML/YAML, декодирование PNG/JPEG/WebP, размеры и дубли, некоторые ссылки между страницами Sitemap; прочие файлы учтены по типу/размеру. Не выполнялся полноценный аудит истории Git на секреты и лицензионных прав, реальное нагрузочное тестирование, тест всех URL/браузеров, Lighthouse, полевой Core Web Vitals, внешнее сканирование уязвимостей или аудит кабинетов. Нет доказательств, что все сценарии работают без ошибок.
- В проверке есть 91 JS, 28 MJS, 1 CJS, 62 Python, 63 HTML, 23 CSS, 25 JSON и 15 YAML; остальные — изображения, шрифты, данные, документы и ресурсы. 90 файлов расположено в `tests/`. Счёт по файловым расширениям, не по реальному языку каждого файла.

## Что подтверждено и что рекомендуется

### P0 — безопасность и корректность перед масштабированием

1. **Статические кабинеты не защищены сервером.** `cabinet.html` использует флаг `promo_logged` в localStorage; это интерфейсное состояние, а не авторизация. Другие `noindex` панели также нужно считать потенциально доступными по прямому URL. Не хранить в них чувствительные данные и не считать скрытие из поиска защитой. Разделить публичный сайт и личную систему: отдельный закрытый сервис с настоящей серверной авторизацией и правами доступа либо оставить личную работу исключительно локальной. Не удалять панели и пользовательские данные без плана миграции. Публичный Firebase-конфиг сам по себе не доказывает утечку секрета, но правила доступа и настройки Firebase нужно отдельно проверить в кабинете.
2. **Аналитика в PR не равна работающей аналитике на сайте.** Ветка добавляет выбор посетителя и счётчики после согласия, а в GA4 на девяти страницах по-прежнему возможны автоматические события, зависящие от настроек сервиса. Нужны проверка конфиденциальности, настроек GA4/Метрики и реальная проверка сети/DebugView после публикации. Отказ может уменьшить статистику; при отзыве настройка перезагружает страницу, но не удаляет уже записанные сторонние cookies. Технический механизм не равен юридической оценке.
3. **Наблюдение за автоматизациями.** В GitHub `Collect HH Market Analytics` активен, недавний запуск `45403733707` завершился ошибкой; ранее получался HTTP 403. Не обходить ограничения и не подменять данные. Проверить актуальный статус, целесообразность расписания и безопасную паузу по решению владельца. `Update News` активен каждые 30 минут и содержит шаг Google Alerts; `Send Telegram Digest` вручную отключён. Не менять состояние сторонних сервисов или рассылок незаметно.
4. **Регрессионный CI.** На снимке `265c854e` проверка Site checks падала на ожидании навигации в новом браузерном тесте. Поправлено ожидание теста в `3c5dfbfd`, локально Chromium прошёл; GitHub run `45588532360` завершился success. Это проверяет тестовый сценарий с заглушками, а не реальную доставку Метрики.
5. **Управление публичными данными.** `_config.yml` исключает `audit/` и `data/google_alerts.json` из GitHub Pages, но не из публичного Git и его истории. Проверить, нужны ли в публичном репозитории исторические данные; исключение из Pages не отзывает уже доступные копии. Не удалять или переписывать историю без отдельного плана и резервной копии.

### P1 — потенциальное ускорение без смены технологии

1. **Портрет на пяти разделах:** `wiki.html`, `tools.html`, `calculators.html`, `projects.html`, `certificates.html` используют `images/photo-right.jpg` размером 1 199 515 байт, указаны размеры 2688×3456, нет `srcset` и `loading`. На главной уже применены варианты 480/640 пикселей, 32 684/47 138 байт. Можно подготовить отдельные адаптивные варианты и применить подходящие размеры по реальному отображению, сохранив качество. Имеющаяся WebP-версия 715 738 байт — не готовая оптимизация для всех размеров. Предполагаемая экономия трафика, а не измеренное улучшение скорости: до/после измерить на мобильной сети и проверить внешний вид.
2. **Лента новостей:** `data/news.json` — 1 132 874 байта без учёта сжатия. `trends.html` добавляет к URL текущую метку времени, поэтому адрес меняется при каждой загрузке и обычное повторное использование кеша по URL ограничено. Рассмотреть версионирование по содержимому/обновлению, ETag или стабильный URL с разумной политикой кеша, а также выдачу страниц/сводного индекса. Перед этим проверить доступные заголовки GitHub Pages и сохранить актуальность новостей.
3. **Каталог промптов:** `data/prompts.json` — 2 760 338 байт до сжатия и разбирается целиком. В `prompts.html` загрузка уже отложена до взаимодействия/видимости каталога — это плюс. Если каталог реально используется медленно, измерить на слабом телефоне и рассмотреть разбиение по категориям или облегчённый индекс поиска. Удалять материалы и менять формат API без совместимости не нужно.
4. **Медиа:** `videos/about.mp4` занимает 6 672 624 байта в репозитории; это не доказывает, что видео скачивается на главной или тормозит её. Для реально используемых видео проверить `preload`, адаптивное разрешение и сжатие. Не удалять большой файл только из-за размера.
5. **Повторяемые HTML/CSS:** несколько старых страниц имеют собственные большие встроенные блоки. Аккуратно выделять общий код по мере правок, не ломая адреса и внешний вид. Но встроенный критический CSS главной — осознанная оптимизация, проверяется синхронизацией с `css/executive.css`; механически выносить его без замеров не следует.
6. **Бюджеты и замеры:** добавить повторяемую проверку веса популярных страниц и сетевых запросов для мобильного и desktop до/после; дополнительно проверять полевые Core Web Vitals в доступных отчётах. Локальные размеры файла ≠ фактические байты по сети и ≠ LCP/INP/CLS.

### P2 — устойчивость и сопровождение

1. `data/manual_news.json` содержит только перевод строки и не является корректным JSON. Прямых ссылок на `data/manual_news.json` как источник в проверенном коде не найдено; это не доказывает отсутствия внешних потребителей. Установить назначение и только затем заменить на допустимое пустое значение подходящего типа или удалить с сохранением совместимости.
2. `js/analytics.js` фактически содержит HTML, а не JavaScript. Тесты обращаются к нему как к старой странице. Не переименовывать автоматически: сначала определить, нужен ли URL и нет ли внешних ссылок, затем изолировать или заменить с проверкой совместимости.
3. Найдены точные бинарные дубли `images/photo-right.jpg` / `images/photo.jpg` и соответствующие WebP. Ссылки могут требовать оба имени; не удалять файл автоматически. Для сокращения технического долга сначала проверить все ссылки и внешние использования.
4. README большой и местами исторический: например, встречаются описания прежней подготовки аналитики, тогда как новая ветка меняет архитектуру. Сделать один актуальный короткий раздел «как запустить / что опубликовано / что в PR / как проверить», остальное перенести в архив с датами. В отчёте о текущей аналитике уже есть предупреждение о старых статусах, но их следует последовательно обновить после принятия решения о публикации.
5. Сократить несогласованность фактов: на `index.html` и в `server/assistant.js` упоминаются переезд в Санкт-Петербург или ЯНАО, в текущих целях приоритет — Сургут и ХМАО, командировки и переезд при релокационном пакете. Сверить публичные тексты портфолио с предпочтениями владельца; **резюме не менять и не пересматривать**.
6. Инвентаризация CSP по 33 страницам нашла 15 inline-скриптов, 57 inline-обработчиков, 52 inline-style атрибута и 19 style-блоков. Это не список уязвимостей. Перед внедрением строгой CSP сначала уменьшить inline-код, протестировать Content-Security-Policy-Report-Only и реальные запросы, затем безопасно усиливать политику без поломки инструментов.
7. Архитектурно логично отделить публичный контент, локальные панели и интеграции. Разделение можно сделать постепенно: явные правила публикации, каталоги, документация и отдельные проверки. Массовый перенос всех файлов, удаление старых URL, монолитная миграция или смена языка сейчас не обоснованы и создадут риск для SEO и текущего функционала.

## Фактические проверки

- AST Python: 62; JavaScript/MJS/CJS: 119 успешных проверок Node плюс один файл HTML под расширением JS; JSON: 25 успешных и один некорректный пустой; XML: 2; YAML: 15; изображения PNG/JPEG/WebP: 48, декодер не нашёл ошибок. Проверка синтаксиса не доказывает логику.
- `npm audit --audit-level=high`: на момент запуска 0 известных уязвимостей по данным npm для текущего набора зависимостей; это не аудит Python, сторонних CDN, приложения или всей цепочки поставок.
- Локально `npm test`: Node 256 тестов, 254 прошли, 2 пропущены; Python 148 тестов, 11 пропущены; калькуляторный набор успешно. Chromium: 5 тестов успешно, в том числе тест аналитики с заглушками. Отчёт относится к проверенному состоянию ветки, а не production.
- Проверки Sitemap, JSON-LD/hreflang guard, статические якоря между 33 страницами и синхронизация CSS прошли; это не подтверждение индексации и не проверка всех внешних ссылок.
- Яндекс ранее показал старую ошибку Sitemap при 16 URL, затем в анализаторе текущая карта на 33 URL прошла без ошибок. Регион Сургут отправлен на рассмотрение, результат неизвестен; переобход страниц обработан, изменение базы поиска ещё требуется проверить.

# Сервер очереди на согласование

Статус последней проверки: рабочий тестовый бот и D1 подключены; текст, фото с телефона и созданная PNG-карточка через `gallery-submit` / `/intake` доставлены на согласование в личный чат. Тестовую PNG-карточку отклонили; `/status` затем показал 0 ожидающих, 0 неопределённых, 2 отправленных и 2 отклонённых. Основной канал не подключён. В staging успешно проверено чтение `/availability` с тестовым секретом; защищённая запись `/intake-one` и конкурентность на реальной D1 ещё не испытаны. Подбор и ежедневная подготовка неподтверждённой галереи реализованы; автоматической отправки по расписанию, AI-редактуры и интерфейса восстановления нет. Источники, права и факты проверяет человек.

## Защита и границы

* `REVIEWER_ID` — числовой **личный** Telegram user ID, используемый и как ID приватного чата; перед отправкой в этот чат пользователь должен открыть бота и нажать Start. ID канала — `CHANNEL_ID`. Эти значения хранятся как секреты, не в Git.
* Bot API token, секрет webhook и секрет приёма хранятся только в секретах Worker. Webhook проверяет Telegram `X-Telegram-Bot-Api-Secret-Token`, user ID, тип чата, ID чата и ID сообщения. Два разных случайных секрета длиной не менее 32 символов (`A-Z`, `a-z`, `0-9`, `_`, `-`). Не вставляйте в конфигурацию, Git, скриншоты, лог, URL или чат.
* `/intake` принимает только POST JSON с заголовком Authorization Bearer и полями `text` и `source_url`; этот секрет выдаётся только доверенному отправителю. Рекомендуется отдельный бот: существующая интеграция Telegram → Сетка не меняется. Переустановка webhook для существующего бота может отключить его прежнюю обработку обновлений; не делайте этого без проверки.
* D1 уникально ограничивает URL. Повторный клик обрабатывается атомарным переходом из `ready`. Все сообщения — простой текст, а не HTML. Дубликаты с разными URL возможны; источники и факты нужно проверять вручную.
* `notifying` и `sending` — неопределённые состояния: ответ Telegram мог потеряться после успешной отправки. Бот **не повторяет отправку** и не пытается сам решить, что произошло. Сначала вручную проверьте личный чат или канал и базу. Не переинициализируйте и не сбрасывайте журнал: процедура безопасного восстановления ещё не реализована. Если удалось отправить в канал, а запись в БД не удалась, запись остаётся `sending`.
* Долговременная доступность облака, квоты, задержки, резервные копии, защита аккаунта и права бота в основном канале не проверены. Одна тестовая PNG доставлена в личный чат; это не проверка доставки в канал. Гарантия exactly-once невозможна. Не включать текущий автоматический workflow, пока новый процесс не пройдёт проверку.

План безопасной настройки сборок: [GITHUB-BUILDS.md](GITHUB-BUILDS.md). GitHub подключён; производственные и preview-сборки выключены.

Из корня: `node --test tests/telegram-review.test.mjs` и `node --check telegram-review/worker.mjs`. Обычные тесты используют подставные базу и Telegram API. ## Настройка нового экземпляра и оставшиеся проверки

1. Бесплатный аккаунт Cloudflare, проверка действующих ограничений и доступности регистрации; без перехода на платный тариф. Для новой D1-базы применить `schema.sql`. Если база уже создана по старой схеме, сначала сделать резервную копию и применить `migrations/001-add-photo.sql` ровно один раз. Не применять эту миграцию к новой схеме, не сбрасывать таблицу. Проверить состояние и резервную копию до любых операций.
2. Локально скопировать `wrangler.toml.example` в игнорируемый `wrangler.toml`, указать ID базы; создать секреты Worker `BOT_TOKEN`, `WEBHOOK_SECRET`, `INTAKE_SECRET`, `REVIEWER_ID`, `CHANNEL_ID` через защищённый механизм поставщика. Не хранить их в Git и не отправлять в переписку.
3. Создать и настроить отдельного Telegram-бота, открыть с ним личный чат, предоставить необходимые права в **тестовом** канале. Развернуть Worker, зарегистрировать webhook с секретом и провести проверку в тестовом канале, а не в основном. Не печатать URL Bot API с токеном в логи.
4. Сначала проверить передачу текста и изображений с настоящими Telegram и D1, реализовать наблюдение за ошибками и процедуру сверки неопределённых состояний; затем проверить границы доступа, безопасность и кнопки. Проверить, что в канал не попадает ничего до нажатия. Только после этого отдельно решать о подключении основного канала.

Бесплатные лимиты и условия проверяются на день подключения: https://developers.cloudflare.com/workers/platform/limits/ и https://developers.cloudflare.com/d1/platform/pricing/ . При исчерпании бесплатных лимитов система может остановиться; платный тариф не подключать без отдельного согласия.

## Подготовка и отправка одного черновика

Эти команды вручную готовят **один** черновик и после отдельного подтверждения передают его в очередь; автоматически не запускаются и не включают старую рассылку. Сначала нужен настроенный Worker, отдельный тестовый канал и проверенные секреты. До этого можно выполнить только первые шаги, не обращаясь к сети.

1. `node telegram-review/drafts.mjs list` показывает индексы текущего `data/news.json`. Список не учитывает журнал отправок: новость может уже быть опубликована. Поскольку файл обновляется, перед созданием убедитесь, что индекс указывает на нужную запись.
2. Создайте игнорируемую папку `private-drafts` и выполните `node telegram-review/drafts.mjs prepare 0 private-drafts/draft.json` (замените 0 нужным индексом). Файл создаётся только если его ещё нет. Это локальный черновик — он не меняет ленту и никуда не отправляется.
3. Откройте JSON, проверьте первоисточник и права, исправьте заголовок и описание, заполните `comment` своим выводом. Только после проверки установите `ready_for_review` в `true`. Это согласие **отправить на проверку в личный Telegram**, а не разрешение публикации в канал. Текст не фактчекинг и не AI-резюме.
4. После настройки тестового Worker задайте в защищённом окружении `REVIEW_INTAKE_URL` (HTTPS-адрес Worker на `workers.dev`, путь `/intake`) и `REVIEW_INTAKE_SECRET`. Не добавляйте значения в команды истории оболочки, скрипты, Git или переписку. Затем `node telegram-review/drafts.mjs submit private-drafts/draft.json` отправит **один** запрос. Worker направит черновик на личное согласование. При таймауте или ошибке сначала проверьте чат и журнал: повтор может привести к дублированию; автоматических повторов нет.

Для передачи картинки добавьте `--card private-drafts/card.png` к команде `submit`. Это один PNG 1080 × 1080, не больше 180000 байт; подпись вместе со ссылкой и пометкой черновика должна помещаться в 1024 символа, иначе её нужно сократить вручную. Клиент сверяет метку исходных заголовка, названия источника и URL в PNG с текущим черновиком; при расхождении или отсутствии метки карточку нужно создать заново. Это защита от случайной устаревшей карточки, а не проверка содержимого изображения: метаданные можно изменить или удалить, а Worker напрямую эту сверку не выполняет. Обязательно проверьте картинку и текст вручную. В личный чат придут изображение, текст и кнопки одним сообщением; в канал — только после подтверждения. Один синтетический PNG передан через `gallery-submit` и `/intake` в реальный личный чат и отклонён; отдельная команда `drafts.mjs submit --card` сама по себе в этом испытании не запускалась. Старая рассылка по расписанию должна оставаться выключенной. Локальные черновики в `private-drafts/` игнорируются Git, но не защищены от других пользователей устройства; не храните в них конфиденциальные данные. Проверки: `node --test tests/telegram-review-drafts.test.mjs`.

## Локальные PNG-карточки

`card.py` создаёт квадратную карточку 1080 × 1080 из заголовка и названия источника в подготовленном JSON. Она не читает сеть и не использует платный AI-сервис. Установите бесплатную зависимость в своё виртуальное окружение: `python -m pip install -r telegram-review/requirements-visuals.txt`. По умолчанию используются локальные шрифты DejaVu Sans из `/usr/share/fonts/truetype/dejavu/`; при отсутствии задайте пути к установленным кириллическим TTF-файлам флагами `--font-regular` и `--font-bold`.

Пример: `python telegram-review/card.py private-drafts/draft.json private-drafts/card.png`. Существующий PNG не перезаписывается. В метаданные PNG записывается хеш исходных заголовка и источника (без самого текста); старые карточки без метки потребуется пересоздать. Длинный заголовок может обрезаться с многоточием — обязательно откройте карточку и проверьте читаемость и смысл. Источник, факты и права нужно проверить вручную; программа этого не делает.

**Проверка и ограничение:** одна синтетическая PNG передана через `/intake` и доставлена для согласования в реальный личный чат, затем отклонена. Это не проверка публикации в канал, любых PNG или гарантии укладывания в квоты бесплатного Worker. Примеры и черновики в `private-drafts/` не включаются в Git и Pages.


## Проверка очереди в Telegram

После развёртывания и настройки отдельного бота владелец сможет написать ему **`/status` в личном чате**. Команда показывает количество черновиков по состояниям и до пяти старейших идентификаторов в `notifying` / `sending`, без текста постов и ссылок. Она не меняет данные и не отправляет посты в канал. Другие пользователи и групповые чаты не получают ответ; проверяются также секрет webhook и ID владельца.

`notifying` и `sending` могут означать как текущую операцию, так и зависшую после сбоя. Если состояние не меняется, проверьте личный чат и канал; запись `sent` — состояние журнала, а не независимое подтверждение доставки. Если бот сообщил об ошибке базы или не ответил, проверьте работоспособность Worker/D1 в своём кабинете. `/status` безопасно повторить, но **не повторяйте публикацию, не меняйте запись и не сбрасывайте журнал вслепую**. Для технической сверки можно найти ID из ответа только в защищённом кабинете D1 с запросом на чтение; записи могут содержать текст и ссылки, не публикуйте их. Автоматических оповещений и готового интерфейса восстановления пока нет.

На тестовом Worker команда `/status` проверена с настоящими Telegram и D1. При сбоях Telegram сообщение со статусом может не прийти.

### Сверка отдельной записи

После `/status` владелец может отправить в личный чат `/inspect ИДЕНТИФИКАТОР` (полный ID из списка, через пробел). Бот покажет состояние журнала, дату, ID сообщений, ссылку на источник и фрагмент текста. Команда только читает запись, ничего не переотправляет и не исправляет. Текст и ссылка могут быть сокращены; не пересылайте ответ другим лицам, если материал ещё не публичный. Просмотр по ID и ограничения доступа проверены только на локальных имитациях; реальный `/inspect` ещё не проверен.

Порядок проверки при неопределённой доставке: дождаться завершения операции; посмотреть `/status` и `/inspect`; сравнить сведения с личным чатом и каналом; при необходимости проверить журнал D1 в закрытом кабинете. **Не удалять и не редактировать запись, не повторять отправку и не делать вывод о доставке только по журналу.** Автоматическое восстановление не реализовано.

### Текстовый черновик с телефона

После развёртывания владелец сможет отправить боту **в личном чате** сообщение в формате:

```text
/draft https://example.org/material
Заголовок и проверенный текст поста.
Мой вывод по теме.
```

Бот создаёт запись в том же журнале и присылает отдельный черновик с кнопками. Сообщение в канал уходит только после «Одобрить». Доступны только HTTP(S)-ссылки; дубликат источника блокируется журналом. При ошибке или отсутствии ответа проверьте личный чат и `/status` и не повторяйте отправку вслепую. Команда не создаёт изображения, не подбирает и не проверяет новости автоматически; источник и формулировки проверяет человек. Можно отправить одно изображение именно как фото с этой же командой в подписи. Альбомы и подпись длиннее лимита Telegram отклоняются, бот присылает фото на согласование и использует возвращённый Telegram file_id при отправке. Сверка фото и текста только ручная. Фото-команда проверена с настоящим Telegram и D1, с доставкой в личный чат; реальный канал ещё не проверен.

### Дополнительная проверка локального Worker runtime

`tests/telegram-review-workerd.test.mjs` — необязательный тест в локальном симуляторе Miniflare с D1 binding. В тестовой версии входной точки **все** обращения к Telegram перехватываются заглушкой; токен и данные вымышленные. Проверяются согласование, повторное нажатие и переходы журнала для текстового поста и заголовка тестовой PNG. Настоящий Telegram, настоящая D1, подлинность PNG, сетевые ошибки провайдера и CPU-квоты бесплатного плана этот тест не проверяет.

Тест запускается отдельно командой `node --test tests/telegram-review-workerd.test.mjs` при наличии Miniflare; без пакета явно пропускается. В штатные зависимости пакет не добавлен: проверенная версия симулятора на момент исследования имела предупреждения аудита своих dev-зависимостей. Выбирайте актуальную безопасную версию для изолированной тестовой среды. Основная CI-проверка использует отдельный SQLite-тест без Miniflare.

### Автоматический локальный отбор кандидатов

`node telegram-review/candidates.mjs private-drafts/candidates.json` читает существующий `data/news.json` и создаёт новый JSON-файл с максимум восемью кандидатами по простому словарю тем SCM. Сеть и Telegram не используются, существующий файл не перезаписывается. Список содержит заготовки с `ready_for_review: false` и без комментария; их нельзя отправить прежней командой submit без отдельной подготовки. Отбор может пропустить полезный материал или включить неподходящий, повторные источники с разными URL не распознаются, даты и факты не проверяются, журнал уже отправленных сообщений не учитывается. Он не генерирует авторские выводы и не отправляет карточки. Каждый материал необходимо проверить и вручную дополнить перед отправкой на согласование. Автоматического планировщика и прямого подключения к очереди эта команда не включает.

### Локальная галерея кандидатов с карточками

После создания подборки установите Pillow и выполните `python telegram-review/cards_batch.py private-drafts/candidates.json private-drafts/gallery`. Создаётся новый каталог с `index.html`, отдельными JSON и PNG (с меткой соответствия черновику). Все JSON остаются неподтверждёнными и без авторского вывода: никакой сетевой передачи или публикации нет. Откройте `index.html` локально, проверьте читаемость карточек, факты, источники и права. Карточки генерируются из заголовков ленты и могут обрезать текст; метка не подтверждает правильность содержания. Галерея помечает номера возможных повторов внутри текущей подборки: одинаковый длинный заголовок после нормализации или совпадение URL после удаления фрагмента и распространённых рекламных меток. Это только подсказка — материалы не удаляются и не изменяются, совпадение может быть случайным, а другие повторы могут остаться незамеченными. Журнал D1 и прежние подборки при этом не проверяются. Перед использованием через `submit` необходимо отдельно заполнить и проверить JSON; клиент проверит также ограничение размера PNG и подписи. Скрипт не перезаписывает существующий каталог; при ошибке создания может остаться неполная галерея — проверьте её вручную. Храните созданные файлы в `private-drafts/`, они исключены из Git и Pages, но не защищены от других пользователей устройства.

### Передача выбранной карточки из галереи

`node telegram-review/gallery-submit.mjs private-drafts/gallery 1` проверяет готовность `draft-01.json`, собственный вывод, метку и размер `card-01.png` и показывает локальный текст без сетевого запроса. Только после ручной проверки источника, прав, текста и карточки можно заполнить комментарий в JSON и выставить `ready_for_review: true`. При изменении заголовка, названия источника или URL карточку нужно пересоздать. Явный `--send` передаёт **один** черновик с карточкой в личную очередь через тот же закрытый `/intake`; нужны `REVIEW_INTAKE_URL` и `REVIEW_INTAKE_SECRET` в защищённом окружении. Публикация в канал потребует отдельной кнопки. При ошибке проверьте чат и `/status`; не повторяйте запрос вслепую. Скрипт не запускается по расписанию и не подбирает авторский вывод. Локальный сквозной тест использует SQLite и подставной Telegram; дополнительно один синтетический PNG через этот клиент и `/intake` реально доставлен в личный чат и отклонён. Это не тест основного канала.

### Подготовка подачи по журналу

Новый закрытый `POST /availability` использует тот же `INTAKE_SECRET`, что и `/intake`, и только читает D1: возвращает наличие до 20 заданных URL, количество ожидающих и неопределённых записей. Тексты и другие записи не возвращаются. `queue-producer.mjs` использует эту проверку, выбирает первый ещё не учтённый вручную подготовленный JSON с карточкой и при явном `--send-one` делает не более одной попытки передачи в личную очередь. Автоматического расписания или генерации авторского вывода нет; `ready_for_review` и содержательный комментарий обязательны. При ожидающем решении или неопределённом результате новая запись не отправляется. Ошибка, таймаут или неоднозначный результат — повод проверить чат и `/status`, не повторять вслепую.

Проверить подготовленные материалы **без передачи** можно командой `node telegram-review/queue-producer.mjs <каталог> --check`. Она проверяет только JSON с `ready_for_review: true` и соответствующие PNG, затем делает один закрытый запрос на `/availability`, не вызывает `/intake` или Telegram и не изменяет журнал. Для непустого набора нужны `REVIEW_INTAKE_URL` и `REVIEW_INTAKE_SECRET`; не выводите значения и не храните их в репозитории. Результат содержит номера проверенных черновиков (`items`), для каждого `known` — наличие точного URL в журнале, `pending` и `uncertain` — счётчики, и `next` — номер первого ещё не учтённого материала при свободной очереди. `candidate` — только предварительная подсказка, не подтверждение фактов, прав, уникальности новости или разрешение на отправку. `pending` / `uncertain` означают остановку, `all-known` — все проверенные URL уже есть. `none-ready` означает, что пригодных JSON нет и запрос вообще не выполнялся: это **не** подтверждение пустой очереди. При ошибке не делать выводов о состоянии. Проверка на существующем staging проведена вручную отдельно; именно эта команда пока испытана только локально. Текущий рабочий Worker ещё не поддерживает `/availability`, поэтому там этот режим до обновления вернёт ошибку.

`/availability` остаётся предварительной проверкой: между ней и вставкой состояние может измениться. Поэтому producer использует отдельный закрытый `POST /intake-one`: один SQL-запрос вставляет запись только если нет состояний `ready`, `notifying`, `sending`. Параллельные запросы этого маршрута не должны одновременно занять пустую очередь. Если Worker старый и маршрута нет, producer получает ошибку и **не переключается** на обычный `/intake`.

В новой версии Worker один атомарный SQL-запрос защищает **все** пути подачи: `/intake`, `/intake-one` и личную команду `/draft`, в том числе при параллельном запуске. Если уже есть запись `ready`, `notifying` или `sending`, новый черновик не создаётся. Это изменение поведения ручной подачи: сначала нужно принять решение по ожидающему черновику либо сверить неопределённую операцию. Удалять или менять зависшие записи автоматически нельзя. В уже развёрнутых старых версиях ручная подача пока может обходить эту защиту. Одобрение может освободить очередь между запусками; ограничение не означает «одна публикация за период». Одинаковый URL блокирует уникальный индекс, но разные URL одной новости не обнаруживаются. При отказе или неопределённом ответе проверяйте чат и журнал, не повторяйте вслепую; exactly-once не гарантируется. Планировщик автоматической передачи в очередь не создан. Единый SQL проверен локально на SQLite и симулированном Worker, но конкурентность удалённой D1 и `/intake-one` не испытаны. В текущей staging-версии вручную проверено только чтение `/availability`; новая общая защита всех путей туда ещё не развёрнута. В рабочем Worker `/availability` и `/intake-one` также пока не развёрнуты. Не включать расписание подачи и не использовать основной канал до отдельной проверки.

### Необязательная локальная проверка workerd

`tests/telegram-review-workerd.test.mjs` проверяет Worker и локальную D1-совместимую базу через Miniflare с полностью подменённым Telegram: проверку очереди, параллельную защищённую подачу, блокировку неопределённых состояний и ручное одобрение. `npm test` запускает этот тест, если пакет Miniflare уже установлен; иначе явно показывает пропуск. Miniflare не входит в зависимости проекта: для разовой проверки устанавливайте его только во временной среде после проверки версии и её уязвимостей. Локальная эмуляция не доказывает поведение удалённой D1, фактическую доставку Telegram, квоты или готовность production.

### Чтение состояния из staging без отправки

Владелец выполнил эквивалентную проверку вручную из PowerShell: без авторизации HTTP 403, с тестовым секретом HTTP 200, `known: false`, `pending: 0`, `uncertain: 0`. Это не запуск данного скрипта и не испытание записи или Telegram.

`staging-smoke.mjs` — отдельная проверка только для предполагаемого адреса `https://scm-telegram-review-staging.965910.workers.dev/availability`; адрес зафиксирован в коде, чтобы случайно не направить секрет в production или на произвольный хост. Адрес подтверждён на экране тестового Worker. Запуск требует явного флага `--confirm-staging-read-only` и переменной окружения `SCM_STAGING_INTAKE_SECRET` с **тестовым** секретом staging; не используйте production-секрет и не помещайте значение в команду, Git, логи или переписку. Команда: `node telegram-review/staging-smoke.mjs --confirm-staging-read-only`.

Проверка сначала отправляет на `/availability` запрос без авторизации и ожидает отказ, затем отправляет с авторизацией случайный синтетический URL `example.invalid` и проверяет формат ответа. Журнал не изменяется и Telegram не вызывается. Результат может показать количество ожидающих и неопределённых записей, но не доказывает, что привязана нужная D1, что сохранены другие секреты, что работают `/intake-one` и доставка, или что production готов. Ошибка или недоступный маршрут — не подтверждение состояния очереди. После выполнения удалите тестовую переменную из окружения. Без сетевого доступа к Worker или без корректно настроенных staging-секретов тест не выполнится. Прежде чем пробовать, нужно отдельно подтвердить адрес, настройки и активную версию тестового Worker; загруженная сборка не становится активной автоматически. Ничего не развёртывать и не переключать webhook ради этой проверки без отдельной сверки.

### Отдельная проверенная заготовка без редактирования JSON

После просмотра галереи, проверки источника, фактов, прав, текста и карточки можно записать собственный вывод в локальный UTF-8 файл, например `private-drafts/comment.txt`, и подготовить копию одного элемента:

```text
node telegram-review/prepare-reviewed.mjs private-drafts/gallery 1 private-drafts/comment.txt private-drafts/reviewed-1 --confirm-checked
node telegram-review/gallery-submit.mjs private-drafts/reviewed-1 1
```

Первая команда создаёт **новый** каталог с `draft-01.json` и копией `card-01.png`; исходная галерея не меняется. Флаг означает, что человек действительно проверил материал, а не разрешает публикацию. Вторая команда только показывает текст локально: проверьте его ещё раз, поскольку клиент очищает разметку и пробелы. Вывод обязателен, максимум 1000 символов; полный текст с подписью должен помещаться в лимит Telegram. При изменении заголовка, источника или URL требуется пересоздать карточку. Метка карточки не подтверждает факты, права или соответствие изображения.

Ни одна из этих команд не обращается к сети и не отправляет сообщений. Для отдельного последующего действия существуют явные режимы отправки `gallery-submit --send` или `queue-producer --send-one`; они требуют настройки и проверки реального сервиса, а для публикации по-прежнему нужна кнопка в личном Telegram. При ошибке записи может остаться неполный новый каталог: не используйте его без проверки. Храните черновики и выводы в `private-drafts/`; исключение из Git не защищает файлы от других пользователей устройства.

### Регулярная подготовка неподтверждённой галереи

Workflow `Prepare Telegram gallery (no sending)` в `.github/workflows/prepare_telegram_gallery.yml` снова включён после слияния ограничений ATI. На основной ветке ежедневно около **06:17 UTC** создаёт максимум восемь кандидатов и PNG-карточек из текущего `data/news.json`. Также предусмотрен ручной запуск через GitHub Actions. Результат — артефакт `unapproved-telegram-gallery` с HTML, PNG и JSON, срок хранения 3 дня. Его можно скачать со страницы запуска workflow. GitHub Actions может задержать или пропустить запуск, отключить расписание при неактивности репозитория или исчерпать квоты; это не гарантированный планировщик доставки.

Workflow использует только публичную ленту, имеет права чтения репозитория, не получает секреты, не пишет в Git и не обращается к Telegram или D1. Галерея содержит **непроверенные** тексты и ссылки; не добавляйте к ней закрытые сведения, поскольку файлы сохраняются в GitHub Actions с доступом согласно настройкам репозитория. В каждом JSON `ready_for_review: false`, комментарий пустой. Ни одобрения, ни авторского вывода, ни сообщения в личный чат или канал этот workflow не создаёт. Использование артефактов и минут может расходовать квоты GitHub.

Материалы `logistics360.ru` и записи с обозначением «Логистика 360» временно исключены из автоматического отбора: [правила источника](https://logistics360.ru/copyright-rules/) запрещают автоматизированное извлечение без разрешения. Это не удаляет старые записи, материалы сайта или предыдущие артефакты и не является юридическим заключением. Возврат источника — только после выяснения прав. Материалы домена `ati.su` и его поддоменов и записи с обозначением ATI/АТИ тоже исключены из новых подборок по решению владельца до уточнения условий. [Соглашение ATI.SU](https://ati.su/policies/agreement/) ограничивает автоматизированные скрипты участников; его применимость к новостному разделу и анонимному сбору не установлена. Старые артефакты при этом не меняются. Другие источники также требуют отдельной проверки условий.

Перед использованием скачайте галерею, проверьте факты, права, источник и карточку, сопоставьте материал с журналом и другими URL той же новости, добавьте собственный вывод и выполните отдельное согласование. Автоматический подбор не читает журнал и может повторять новости каждый день; галерея может предупредить о некоторых похожих материалах внутри одной подборки, но разные адреса одной публикации часто не распознаются. Сама подготовка не подтверждает доставку и не заменяет проверку новой очереди в Cloudflare. Старый `Send Telegram Digest` должен оставаться выключенным.

Последняя ручная проверка workflow в GitHub Actions завершилась успешно и создала артефакт; его содержимое из этой среды скачать не удалось. Запуск именно по расписанию ещё не подтверждён.

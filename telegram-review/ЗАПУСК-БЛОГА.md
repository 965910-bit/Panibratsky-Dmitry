# Ежедневный SCM-блог: что готово и как проверить

Цель: ежедневная подборка SCM и публикация **только после решения владельца в личном Telegram**. Ни одна из приведённых ниже проверок не выполнена в действующем канале автоматически.

## Текущее положение

- По расписанию GitHub около 06:17 UTC формируется неподтверждённая HTML-галерея, а не сообщение в Telegram. Автоматическая доставка подборки владельцу и публикация по расписанию пока не настроены. Расписание Actions может задерживаться или не сработать; успешен последний проверенный ручной запуск, запуск по расписанию пока не подтверждён.
- На локальном снимке `data/news.json` от 17.11.2026 отбор дал **0 кандидатов**. Большинство записей имеет вместо заголовка тему Google Alert; они намеренно не превращаются в посты. Источники ATI и «Логистика 360» исключены до выяснения прав. Это состояние снимка, а не прогноз на следующие дни. Нужны разрешённые, пригодные источники и проверка фактов; не гарантируется ежедневный пост любой ценой.
- Рабочий Worker ранее отправлял тесты в личный чат; реальный основной канал не проверен. Staging и отдельная D1 существуют, но раньше содержали заглушку токена, а активную версию и текущие настройки нужно сверить заново. Единственный webhook каждого бота не переключать без проверки текущего назначения и плана возврата.
- Новые единые ограничения очереди, передача неподтверждённого кандидата и ручная сверка из этой ветки проверены локально, **не развёрнуты**. Для существующей базы нужна проверенная резервная копия и миграция `002-add-reconciliation.sql` по README; к новой базе из `schema.sql` миграции не применять. Не выполнять на рабочей базе до изолированного тестирования и отдельного согласования.

## Подготовка изолированного испытания

Владелец проверяет в Cloudflare и Telegram, не отправляя токены, секреты, ID и скриншоты со значениями:

1. Какая версия активна в `scm-telegram-review-staging`; какая тестовая D1 привязана как `DB`; присутствуют ли пять **имён** runtime-секретов из `GITHUB-BUILDS.md`. Загруженная версия не обязательно активна. Проверить текущую схему и сохранить резервную копию перед миграцией.
2. Что выбранный бот действительно отдельный и его webhook не обслуживает другую систему; что целевой канал — отдельный тестовый канал и бот имеет нужное право публикации. Настраивать webhook тестового бота только после подтверждения назначения и плана возврата; рабочие токен и webhook не переносить в staging.
3. После отдельной проверки конфигурации, миграции и продвижения версии только в staging провести чтение `/availability`, затем передать один уникальный явно тестовый черновик в личный чат. Убедиться, что до нажатия кнопки в тестовом канале ничего нет. Отклонение не публикует, повторный URL блокируется. Использовать другой уникальный материал для проверки одобрения: один пост в тестовом канале, повторное нажатие не создаёт второй пост; проверить `/status` и `/inspect`.
4. Затем проверить фото и параллельную подачу двух разных тестовых материалов: при одной свободной очереди должен пройти не более одного. В случае `notifying` или `sending` не повторять вслепую и не сбрасывать базу; сверить чат, тестовый канал и журнал по README. Реальные сетевые сбои нельзя безопасно имитировать на рабочем канале.

Любая неожиданность — остановиться, не пересоздавать базу и не повторять отправку. Скриншоты должны скрывать токены, значения секретов и личные ID. Только после успеха и отдельного разрешения переходить к настройке основного канала и расписания отправки на согласование. Полный порядок, ограничения и команда ручной сверки: `README.md` и `GITHUB-BUILDS.md`.

## Подготовленный ручной запуск для staging

Новый `.github/workflows/telegram_review_staging.yml` имеет только `workflow_dispatch`: расписания нет. Его не запускали и не включали. Он фиксирован на `https://scm-telegram-review-staging.965910.workers.dev/intake`, требует ввод `STAGING` и GitHub Environment `telegram-review-staging` с отдельным **тестовым** секретом `SCM_STAGING_INTAKE_SECRET` и переменной `SCM_STAGING_ALLOWED_HOSTS`. Секреты не вводить в чат или Git, не использовать production-секрет. Перед запуском независимо сверить адрес, привязку D1, токен и канал: имя environment и URL сами по себе не доказывают изоляцию. Пока в staging остаётся заглушка токена, отправка не заработает.

Автоотбор берёт только HTTPS-адреса на точных доменах из явно заданного списка через запятую (поддомены не включаются автоматически), с датой публикации не старше 48 часов и не из будущего. Действующие запреты источников и фильтр заголовков Google Alert сохранены. Он не запрашивает источники напрямую, а использует текущий `data/news.json`; пустая лента или отсутствие свежих допустимых кандидатов означает отсутствие отправки. Список доменов — ручное разрешение на обработку, не юридическая проверка. Проверить условия конкретного материала и автоматизированного доступа до добавления домена. Если черновиков нет, `none-ready` **не** означает, что D1 или Telegram работают.

Выполнение сначала создаёт неподтверждённую галерею, затем через `/availability` и только `/intake-one` передаёт максимум один новый черновик в личный чат. Занятая очередь, неопределённость или отказ останавливают работу; повторов и fallback на старый endpoint нет. Черновик содержит заголовок, описание и источник без искусственно добавленного «авторского вывода». Владелец проверяет факты, права, текст и карточку, а затем одобряет или отклоняет: по кнопке публикуется **ровно показанный текст**, встроенного редактирования нет. Разные URL одной новости и переупорядоченные запуски не гарантируют отсутствие смысловых повторов. Одобрение между повторными ручными запусками может позволить отправить новый черновик: лимита «один в сутки» нет.

Запуск относится только к изолированному стенду и требует успешных проверок выше. Не запускать повторно после таймаута: сообщение могло дойти. При ручном запуске со сборкой этого репозитория GitHub Actions передаёт данные в staging, поэтому workflow нельзя считать чисто локальным. Страница запуска может не показывать файл новой ветки до появления workflow в default branch; не сливать и не продвигать версию без проверки изменений. Автоматическое ежедневное расписание подачи, надёжное ограничение по дню и запуск для рабочего канала ещё не созданы.

## Предложения источников для дальнейшей проверки

- [Eurostat: новости по транспорту и RSS](https://ec.europa.eu/eurostat/web/rss) — официальная статистика, в основном на английском; сообщения не обязательно выходят ежедневно. [Правила Eurostat](https://ec.europa.eu/eurostat/help/copyright-notice) разрешают повторное использование редакционных материалов ЕС с указанием источника и изменений при условиях CC BY 4.0; есть исключения для материалов третьих лиц и отдельных наборов данных, для переводов указаны дополнительные условия. Проверять конкретный материал и автоматизированный доступ.
- [UN Trade and Development: обзор морских перевозок](https://unctad.org/system/files/official-document/rmt2025_en.pdf) — аналитика международной торговли и портов, но в этом конкретном отчёте указано all rights reserved: для воспроизведения выдержек нужно выяснить разрешение. Это источник для ручного изучения, не подключённая лента.
- [Всемирный банк: транспорт и порты](https://www.worldbank.org/ext/en/topic/transport/shipping-and-ports) — возможные темы для ручного отбора. [Общие условия](https://www.worldbank.org/ext/en/legal/terms-conditions/reproduction-and-use) требуют предварительного разрешения для воспроизведения, перераспределения или коммерческого использования, если не указано иное. Не включать автоматически без проверки конкретного материала и разрешения.

Это предложения для оценки, не подтверждение прав на копирование или рекомендации подключить всё подряд. Ни один источник автоматически не добавлен; для ежедневного русскоязычного блога потребуется согласовать другие допустимые каналы и порядок перевода, иначе подборка может часто оставаться пустой.
